### ✅ NFR-1 — Row-level authorization

> Authorization is checked on every request, against the specific record being touched. "Is this user logged in" is not enough; the question is always "is this user allowed to do this, to this row". Write it once in a place you can reason about rather than scattering checks through every handler.

**Status:** ✅ Done.

Role-based checks are centralized (`requireAuth` / `requireRole` middleware). Record-level scoping now has two proven implementations: `requireUserScope` for the `users` domain (manager/HR visibility over `users` rows), and `leaveRequestService.js` → `resolveActingCapacity(actor, request, action)` for leave requests — one function, called by every approve/reject/withdraw/cancel/override action, deciding whether the actor is the owner, HR, the employee's direct manager, or an active delegate. Neither domain has authorization logic duplicated across handlers.

Proven by tests, not just by design: `leaveRequests.test.js` has dedicated cases for a manager acting outside their team (404), an employee approving their own request (403), and a delegate acting after their window expired (404) vs. during it (200).

### ✅ NFR-2 — Balances must never drift

> A balance must never drift. The number an employee sees has to agree with the history that produced it, after any sequence of approvals, cancellations and overrides. Consider whether a balance is something you store and mutate, or something you derive from a ledger of entries.

**Status:** ✅ Done — built on the ledger, not a mutate-in-place total.

`leave_balances` (see [`docs/3.db.md`](3.db/README.md)) stores only `entitlement` per user/type/year — migration `014_create_leave_balance_ledger.sql` dropped the old `days_taken`/`days_pending` columns. Every leave-request action (submit/approve/reject/withdraw/cancel/override) writes one append-only row to `leave_balance_ledger` with a signed `pending_delta`/`taken_delta`, and the displayed balance is always a `SUM()` over those rows (`leaveBalanceRepository.js`). There's no running total that could ever fall out of step with the history that produced it, because the number *is* the history, recomputed every read.

Proven by tests: `leaveRequests.test.js` checks the balance after submit, approve, reject, withdraw, cancel, and an HR override in both directions.

### ✅ NFR-3 — Server-side state machine

> State transitions are enforced server-side. The set of legal moves from each state should be visible in one place in the code, not implied by scattered conditionals.

**Status:** ✅ Done.

`server/src/services/leaveRequestStateMachine.js` is a single explicit map (`{ action: { from: [...], to: status } }`) covering every legal transition — `APPROVE`/`REJECT`/`WITHDRAW` from `SUBMITTED`, `CANCEL` from `APPROVED`, and the two HR-override transitions between `APPROVED`↔`REJECTED`. Every mutating endpoint calls `assertLegalTransition(action, currentStatus)`, which throws a `409` for anything not in the map — there is no other code path that changes a request's status. `WITHDRAWN`/`CANCELLED` never appear as a `from`, which is what makes them dead ends. Tested directly: `leaveRequests.test.js` asserts that approving an already-withdrawn request is rejected with `409`.

### ✅ NFR-4 — Server-side validation on every write

> Every write endpoint validates its input server-side. Never trust the client.

**Status:** ✅ Done, for every endpoint that exists today.

Every `POST`/`PATCH`/`DELETE` route runs a Zod schema via `validateBody`/`validateParams`/`validateQuery` (`server/src/validators/*.js`, wired in `server/src/routes/*.js`) before the controller ever sees the request. Module 3's `leaveRequestValidator.js`/`delegationValidator.js` followed the exact same pattern with zero exceptions — including a `.superRefine` catching a single-day request with both half-day flags set, and every date-range endpoint checking `endDate >= startDate` server-side regardless of the `<input min>` HTML hint on the frontend.

### ✅ NFR-5 — Meaningful status codes & distinguishable errors

> The API returns meaningful HTTP status codes and machine-readable error responses. A refused action returns a distinguishable error — "not allowed" and "not found" are different answers, and you should decide deliberately which one an outsider gets.

**Status:** ✅ Done, as a reusable pattern.

`server/src/utils/appError.js` provides named helpers — `unauthorized()` (401), `forbidden()` (403), `notFound()` (404), `conflict()` (409), `badRequest()` (400/422) — and `server/src/middlewares/errorHandler.js` maps any thrown `AppError` (plus raw Postgres constraint violations) to a consistent `{ success, message, errors }` envelope.

**The Module 3 decision, made:** `leaveRequestService.js` returns **404** whenever the actor has no legitimate reason to know a request exists at all (an unrelated manager, an unrelated employee, or a delegate whose window has expired) — including that last case, where "used to have access" is treated the same as "never had access," since the practical security outcome is identical and it avoids a more complex "was this ever valid" lookup. It returns **403** when the actor already knows the request exists (because it's their own) but this specific action isn't theirs to take — e.g. an employee approving their own request.

### 🟡 NFR-6 — Code must be commented

> Code must be commented. Every file opens with a short comment saying what it is for, every exported function has a description of its inputs, output and failure modes, and every non-obvious piece of logic — the permission rules, the working-day calculation, the balance arithmetic, the delegation window — carries a comment explaining why it works that way. Comments that merely restate the code are noise; we will call those out too.

**Status:** 🟡 Partial — modules 1–3 retrofitted, modules 4–5 and the repository layer still outstanding.

Some non-obvious logic already carried a "why" comment from the start (e.g. the cookie `SameSite`/`secure` reasoning in `server/src/utils/cookies.js`, the invite-expiry design in `invitationService.js`).

**The modules 1–3 retrofit is done**: across the 24 service, controller and validator files covering accounts/roles/reporting/invitations, leave types/balances/calendar, and leave requests/approvals — **24/24 now open with a file-header comment** (was 9/24) and **141/144 exported functions carry an input/output/failure-mode description** (was 82/144). The three exceptions are `reject`/`withdraw`/`cancel`, three one-line exports from a shared factory that sit directly beneath one comment covering all four — splitting that into four near-identical blocks would be exactly the noise this NFR warns about.

Two properties of that pass are worth recording. It was **comment-only by construction** — 425 lines added, **zero deleted**, verified per file, so the diff itself proves no code, structure or control flow changed. And the comments were aimed at what a reader can't recover from the code: why `decideLeaveRequest` checks its four failure modes in that specific order, why `passwordResetService`'s un-awaited send and swallowed delivery failure are security decisions rather than sloppy error handling, why `updateEmploymentDates` being HR-only is a boundary rather than a convention, and which apparently-local writes (creating a leave type, declaring a holiday) are actually company-wide.

**Still outstanding:** the module 4–5 files (payroll, salary slips, employee documents, notifications) and the repository layer throughout.

**This is a binding rule** (see `.claude/rules.md`) for every new or changed file going forward — it overrides the general "comment only when non-obvious" default. Every Module 3 file (`leaveRequestService.js`, `leaveRequestStateMachine.js`, `workingDayService.js`, the repositories, validators, controllers, routes) was written to this standard: a file-header comment plus an input/output/failure-mode comment on every exported function, and an explicit "why" on the state machine, the authorization function, the working-day calculator, and the ledger delta logic. Retrofitting every pre-existing pre-Module-3 file is still a tracked backlog item, not something done piecemeal inside unrelated changes.

### 🟡 NFR-7 — Responsive at 200 employees / 3 years of history

> The app stays responsive with 200 employees and three years of requests.

**Status:** 🟡 Partial — indexed, but not measured or paginated.

Some groundwork exists: `idx_users_manager_id`, `idx_leave_balances_user_id`, and now `idx_leave_requests_employee_id`/`idx_leave_requests_employee_status`/`idx_leave_balance_ledger_lookup`/`idx_audit_logs_leave_request_id` (see `docs/3.db.md`) cover the lookups Module 3's endpoints actually run. **Now paginated, still not measured.** The endpoints that grow with time take `limit`/`offset` and return `{ rows, total }` — `GET /leave-requests/team`, `/all`, `/leave-requests` (HR's browse) and `GET /salary-slips` — with the team/approvals pair also accepting a ≤62-day `startDate`+`endDate` window for the calendar, which needs a whole month rather than page 1. Counts are their own endpoints instead of being derived from a fetched list, and `idx_leave_requests_employee_start_date` lets a page be walked in index order rather than sorting the whole match set per page. What stays unpaginated is bounded by headcount or leave-type count rather than by time: every `/mine` endpoint, `/leave-types`, `/holidays`, `/leave-balances/me`, `/delegations/*`, and `/report` + `/report/csv` (one row per employee, and an export should cover everything). No load testing has been performed either way.

The original wording of this requirement, kept because it records what was true before that work: `GET /leave-requests/team`, `GET /leave-requests/mine`, `GET /leave-requests/all`, and FR-024's `GET /leave-requests` (HR's filterable browse) all return every matching row with no limit/offset — fine at 200 employees × a few years of requests, but worth revisiting if any of them is ever expected to grow past a few hundred rows per call. `GET /leave-requests/report`'s aggregation (`GROUP BY` over the same table) has the same characteristic — one row per employee rather than per request, so it scales with headcount, not request volume, but still unpaginated. No load testing has been performed either way.

### 🟡 NFR-8 — Usable on a phone-width screen

> Usable on a phone-width screen. It does not need to be beautiful; it needs to be clear.

**Status:** ✅ Done — the gap found while writing this doc is now fixed.

The navbar wraps (`flex-wrap`), and every card-list page (Holidays, My Requests, Approvals, Delegations) uses a card-per-row layout with no fixed-width table, so they were mobile-safe from the start. `EmployeesPage`, `TeamPage`, and `LeaveTypesPage`'s tables now wrap their `<table>` in `overflow-x-auto` instead of the `Card`'s `overflow-hidden` clipping it, so a phone-width screen scrolls the table horizontally instead of losing columns. `AppHeader`'s identity cluster (avatar/name/role badge/logout) now wraps and hides the plain-text name below the `sm` breakpoint, so it no longer clips on a narrow screen — the avatar initials and role badge alone still identify who's logged in.
