## 🧩 Reusable UI Components

Before writing new markup for a button, badge, card, modal, or page header, check this table — it's almost certainly already covered by one of these primitives in `client/src/components/ui/`.

| Component | Path | Purpose | Key props |
|---|---|---|---|
| `Button` | `ui/Button.jsx` | Every clickable action (submit, primary/secondary/success/danger/ghost actions). Supports rendering as a router `Link` via `as`. Prefer this over `IconButton` for row-level actions in a list (approve/reject/withdraw/etc.) — an icon-only button reads as clutter once a row can carry several actions; label them. | `variant` (`primary\|secondary\|success\|danger\|ghost`), `size` (`sm\|md`), `icon`, `iconPosition`, `loading`, `as` |
| `IconButton` | `ui/IconButton.jsx` | Icon-only actions, e.g. row-level delete/approve. Always requires an accessible `label`, which also drives its hover tooltip (`Tooltip`, below) — never add a native `title` attribute alongside it. | `icon`, `label`, `variant` (`default\|primary\|success\|danger\|ghost`), `size`, `loading`, `tooltipPosition` (`top\|bottom\|left\|right`, default `top`), `tooltipPortal` (forwards `Tooltip`'s `portal` — **required for every icon button in a table or list row**, and already set on all of them; see the ⚠️ note on the employee-table layout fixes for why) |
| `Tooltip` | `ui/Tooltip.jsx` | The on-hover label for **every** icon-only control in the app — wraps `children`, floats `label` near them on hover, styled like the app's own cards (white, bordered, shadowed) instead of the browser's native `title` tooltip (which renders however the OS/browser feels like, often a stark unstyled box with zero visual relation to the rest of the UI). `IconButton` uses this internally; anywhere else a `title`-only tooltip is wanted, wrap with this instead of adding `title=`. Renders nothing extra (just `children`) when `label` is falsy. | `label`, `position` (`top\|bottom\|left\|right`, default `top`), `portal` (renders the label into `document.body` instead of as a CSS-absolute sibling — needed inside any clipping *or* scrolling ancestor), `className` (controls the wrapper's own `display`/sizing — `Tooltip` only supplies `group/tooltip relative`, not `inline-flex`, so callers that need block/full-width behavior, e.g. `NavBar.jsx`'s nav rows, aren't fighting a hardcoded display value) |
| `PasswordInput` | `ui/PasswordInput.jsx` | Drop-in replacement for `<input type="password">`, everywhere one exists (login, change password, accept invite, reset password) — adds a show/hide eye-icon toggle. Forwards every other prop straight to the underlying input. The toggle button's accessible name is plain text content (`sr-only` span), deliberately **not** `aria-label` — an `aria-label` containing "password" would make it match every existing `getByLabelText(/password/i)` test query alongside the real input. | `className` (plus any standard input prop) |
| `Badge`, `RoleBadge`, `StatusBadge` | `ui/Badge.jsx` | Pills for roles/status. `RoleBadge` renders the short label from `ROLE_LABELS` (`HR_ADMIN`→"HR" etc.) instead of the raw enum. `BADGE_BASE_CLASSES` carries `whitespace-nowrap` and that is **load-bearing, not cosmetic** — a badge is an inline `<span>`, so a two-word label ("Super Admin") in a narrow column wrapped mid-pill and split the rounded background into two stacked half-pills. It deliberately sets no `display`: `TeamRequestList.jsx` passes `flex` in via `className`, and two competing display utilities in one class string resolve by stylesheet order, not by the order they're written. Pinned by `ui/Badge.test.jsx`. | `RoleBadge({ role })`, `StatusBadge({ status })` |
| `Card` | `ui/Card.jsx` | White bordered container (table wrappers, form panels, tiles). No default padding — pass it via `className`. | `className` |
| `Modal` | `ui/Modal.jsx` | The only modal/dialog pattern in the app — portal + backdrop + Escape/click-outside close. Use for any "add/edit X" form instead of an inline toggled section. | `open`, `onClose`, `title`, `size` (`md` default, `lg` for content-heavy views like `RequestDetailModal`) |
| `DocumentPreviewModal` | `ui/DocumentPreviewModal.jsx` | The in-app document viewer for **leave request attachments only** (`RequestDetailModal.jsx`) — an `<img>` for an image, an `<iframe>` for a PDF or plain text file (all three render natively, no extra library — see the note below on why a doc-viewer package was tried and dropped), a fallback message for anything else, and an "Open in new tab" link regardless of type. Originally shared by all three document surfaces; the other two (employee-verification documents, salary slips) moved to `DocumentViewerPage` (below) once a modal read as too small for a document someone actually needs to read closely — this one stays a modal since nobody's asked to change it. Always adds a **View** action alongside whatever download option already existed on that page — never replaces it. `document` is `{ url, filename, mimeType }` or `null` (renders nothing) — the caller re-fetches a fresh signed URL right before opening this, since Cloudinary's expire a few minutes after minting (`cloudinaryService.js`). | `document`, `onClose` |
| `DocumentViewerPage` | `pages/DocumentViewerPage.jsx` | The full-page in-app document viewer, at `/dashboard/documents/preview` — an employee's own onboarding document, HR reviewing someone else's, or a salary slip PDF, all render through this **one** page (rendering logic never branches on which) rather than three separate implementations. > ⚠️ **The dashboard home (`DashboardPage.jsx`) is deliberately minimal** — a "Welcome, {name}" greeting plus `DelegationStatus`/`TeamOverviewSummary`/`MyLeaveSummary` stacked underneath, per direct feedback after a richer version (summary cards, a detailed team-requests table, a compact calendar, quick actions) was tried and asked to be removed. Don't re-add those without being asked again — if you want a detailed team-requests table or a leave calendar, `ApprovalsPage`/`TeamRequestList` and `HolidaysPage`/`HolidayCalendar` already cover that elsewhere in the app.

> 📄 **In-app document viewer, added alongside every existing download (never replacing one).** Three surfaces had a document with only a download/external-open action: leave request attachments (`RequestDetailModal.jsx`), an employee's own onboarding documents (`ProfileDocumentUpload.jsx` — its old `ViewLink` did `window.open(url, "_self")`, navigating the *entire app* away to the raw file, arguably the exact bug this feature fixes), and salary slip PDFs (`SalarySlipList.jsx`). One of the three (`EmployeeDocumentList.jsx`, HR's document-review view) already had a working local `DocumentPreviewModal` — extracted to `ui/DocumentPreviewModal.jsx` and reused everywhere instead of building a second implementation. See its row in the table above for the API.
> - **A doc-viewer library (`@cyntler/react-doc-viewer`) was tried and dropped before landing on the plain `<img>`/`<iframe>` approach** — `npm audit` flagged a moderate, unpatched advisory in its own `TXTRenderer` (renders raw file content as a `ReactNode` without sanitizing it, an XSS risk). This app doesn't currently accept text-file uploads anywhere (`ACCEPTED_DOCUMENT_TYPES` is PDF/JPG/PNG everywhere documents are uploaded), so that renderer would never actually run — but authorization/security review is this project's #1 stated review criterion, so the unpatched advisory wasn't worth taking on for a library whose only real benefit (docx/csv/pptx support) nothing in this app produces anyway. Don't re-add a doc-viewer package without checking `npm audit` first.
> - **The employee-verification document surfaces (an employee's own required/custom documents, HR reviewing someone else's) and salary slip PDFs were all moved from `DocumentPreviewModal` to one dedicated full page, `pages/DocumentViewerPage.jsx` at `/dashboard/documents/preview`** — a modal panel read as too small for a document someone actually needs to read closely, and a full page gives it the whole viewport. Only leave request documents (`RequestDetailModal.jsx`) still use the modal — nobody's asked to change that one. See `DocumentViewerPage`'s own row in the table above for its query-param shapes; a salary slip needs no signed-URL fetch (`getSalarySlipPdfUrl(id, { inline: true })` builds the URL directly), the other two do, but the page's rendering logic never branches on which — one consistent UI regardless of document type, deliberately, rather than a second page implementation that could drift from this one.
> - **PDF preview not working at all for the employee-verification surfaces turned out to be a Cloudinary account setting, not a code bug** — traced upload/storage/retrieval line-by-line and found the leave-request-document and employee-document flows byte-for-byte identical (same `resource_type: "raw"` for a PDF, same `getSignedDocumentUrl` call shape). Cloudinary blocks delivery of `resource_type: raw` PDF/ZIP assets by default until "Allow delivery of PDF and ZIP files" is enabled in the account's Settings → Security — an account-dashboard toggle, nothing fixable in this repo. If a document PDF preview ever silently fails again with no code-level explanation, check that setting before assuming a regression.
> - **Bug found and fixed right after shipping: clicking View on a payslip downloaded it instead of previewing it.** Root cause: View and Download both pointed at the exact same `GET /salary-slips/:id/pdf`, which unconditionally set `Content-Disposition: attachment` — a header the browser honors regardless of *how* the URL is loaded (an `<a download>` click, or an `<iframe src>`), so the "preview" iframe triggered a download the instant it mounted. The other two document surfaces never had this problem: their View and Download actions hit genuinely different URLs (a Cloudinary signed URL for View vs. this app's own forced-download proxy, or vice versa for employee documents, which have no forced-download proxy at all). Fixed by adding an opt-in `?disposition=inline` query param to the existing endpoint (`salarySlipController.js`'s `downloadPdf`) — defaults to `attachment` (Download, and any old bookmarked link, is byte-for-byte unchanged), and `client/src/services/salarySlipService.js`'s `getSalarySlipPdfUrl(id, { inline })` builds the `inline` variant only for the viewer page. The query value is never interpolated into the header — anything other than exactly `"inline"` falls back to `attachment` — so this can't become a header-injection vector. **Lesson for the next document type added to this app**: if View and Download for the same file ever end up pointing at one shared endpoint (rather than two, like the Cloudinary-backed ones), check what `Content-Disposition` that endpoint sends — `attachment` will hijack an `<iframe>` preview every time, on any resource type.
>
> 🧾 **Payslip PDF template redesigned to match a reference layout the user provided** (`server/src/services/payslipPdfService.js`) — an employee-summary block + highlighted net-pay box, a PAN/Aadhar identifiers row, a two-column earnings/deductions table with running totals, a total-net-payable band, and an amount-in-words line, all manually x/y-positioned with `pdfkit` (its auto-flow cursor is single-column only, so a genuine two-column layout can't use it). Before implementing, did a line-by-line comparison of the reference image against what `salary_slips` + `users` actually store, then confirmed three data gaps directly with the user rather than guessing:
> - **No company name/logo/address anywhere** — this app has no concept of "the employer's own identity," only employee data. Left off entirely, per direct instruction.
> - **No PF A/C Number or UAN** — only PF *contribution amounts* exist, never an account/UAN number. Per direct instruction, **PAN Number and Aadhar Number print in that row instead** (`users.pan_number`/`users.aadhar_number`, already collected during profile verification) — `salarySlipRepository.js`'s `SLIP_COLUMNS` was extended with `employee_designation`, `employee_code`, `employee_joining_date`, `employee_pan_number`, `employee_aadhar_number` to support this and the summary block.
> - **No Professional Tax line and no year-to-date (YTD) columns** — neither has a source in the data model; adding either was declined in favor of keeping this a presentation-only change with no schema/query work. No distinct "Pay Date" either — only `pay_period` (`"YYYY-MM"`) exists, no separate disbursement-date field.
> - **Currency renders as `"Rs."` not `"₹"`** — pdfkit's built-in Helvetica is a PDF standard-14, WinAnsi-encoded font with no Rupee-sign glyph; a real glyph would need a bundled TTF, out of scope for a presentation tweak.
> - **New `server/src/utils/numberToWords.js` (`numberToWordsIndian`)** for the "Amount In Words" line — hand-rolled rather than a library, since the Indian numbering system (thousand/lakh/crore grouping) is a small enough algorithm on its own and no existing dependency covers it.
> - **`formatPayPeriod` extracted from `notificationService.js` into shared `server/src/utils/payPeriod.js`** — both the payslip PDF and notification messages format the same `"YYYY-MM"` shape and had started drifting into two copies.
> - No API-facing shape changed (still the same route, query params, and headers per `docs/2.api_documentation.md`'s `GET /api/salary-slips/:id/pdf` entry) — only the PDF's internal rendering, so no docs update was needed there.

> 💰 **Payroll period-eligibility and re-run guards, added to `calculatePayroll`/`confirmPayroll`** (`server/src/services/salarySlipService.js`) — three gaps found directly by the user testing the payroll run: a mid-month run computed a *full* month's figures as if it had already finished, HR could run payroll for a month that hadn't even started yet, and re-confirming an already-active period silently overwrote it (no void required). Discussed as a list of standard payroll scenarios before implementing, and scoped down on purpose:
> - **`assertPeriodStarted(payPeriod)` rejects `calculate` and `confirm` with `400` for any period whose first day is after today** — a period with no elapsed days has no attendance/leave data to compute LOP from, so running it isn't "early," it's meaningless. **Mid-month is deliberately still allowed** — the period has started, HR may legitimately want an early preview or run against what's happened so far, and forcing a hard month-end wait was explicitly declined. This is the full extent of the "timing" fix — nothing enforces a cutoff day or blocks far-backdated periods, both left out of scope for this round. **⚠️ Reversed later — see the bullet below: mid-month is no longer allowed at all.**
> - **`confirmPayroll` now checks for an existing `ACTIVE` slip per (employee, pay period) before committing** — a row that already has one is moved into `skipped` with reason `"Already generated for this period — void the existing slip first"` instead of letting `replaceSlipsForPeriod`'s `ON CONFLICT ... DO UPDATE` silently overwrite it. **The guard is confirm-only, not calculate** — `calculatePayroll`'s preview still returns the full computed `"ok"` row for that employee/period even when a confirm right after it would be blocked, so HR always sees what the numbers *would* be, and only finds out at the commit step that it needs a void first. Once voided, `replaceSlipsForPeriod`'s existing archive-then-reactivate behavor is untouched — this only closes the *silent* overwrite path, not the general re-run-after-void one.
> - **`PayrollRunForm.jsx`'s post-approve summary now lists each skipped employee's name and reason**, not just a bare count — because a row can now be skipped at confirm time even after showing "Ready" in the preview (e.g. someone else confirmed that period for that employee in between preview and approve), a plain count would leave HR unable to tell who or why without checking the team's slip list separately.
> - **Deliberately out of scope for this round** (listed for the user, declined for now): re-syncing a slip's LOP when a leave request affecting it is approved/cancelled *after* the slip was generated; whether a regenerate-after-void should use the salary structure as of the *original* period or today's (currently always today's, since `computeSlip` has no concept of "as of a past date"); and proration for an employee who joined or exited mid-period. Revisit these together if backdated corrections becomes a real workflow, not piecemeal.

> 🧾 **G23 — a re-run keeps the salary the period was run with, and the fix needed no migration because the slip already stores it.** `salary_structures` is one row per employee, overwritten on change, with no effective dates — so `computeSlip` could only ever read "the salary now". A re-run therefore recomputed an old month at the current salary, and that mattered far more once **void-and-re-run became the standard correction path** (every leaving date, date correction and stale pro-ration ends in "re-run payroll for those periods"): the mechanism built to make a figure right introduced a different error. Measured: ₹10,000 on a full month for a ₹50,000 employee raised to ₹60,000, and ₹3,225.81 even on a pro-rated exit month.
> - **The basis comes from the prior slip for that period, `ACTIVE` or `VOIDED`** (`salaryBasisFromSlip`). `salary_slips` carries `basic_pay`, `hra`, both PF figures, `esic`, `special_allowance` and `income_tax` — the whole structure, snapshotted at generation — and a voided slip keeps them. The voided case is the important one, since that is what a correction looks like. Resolved from the *same* query `calculateForSubtree` already ran to answer "already generated?", so it costs nothing extra.
> - **The rule to remember: a correction recomputes days, never salary.** Every re-run in this app exists to fix a day count, so holding the salary fixed is what those corrections actually mean.
> - **A current structure is still required**, even when its values are superseded. Its *existence* is what marks someone as on payroll — removing it must stop payment, not let an archive keep paying them.
> - **Rows carry `usedArchivedSalary: true` and the run preview says so.** Without that, "I gave her a raise, re-ran July, and the figure didn't move" reads as a bug rather than as the point.
> - **Deliberate limitation: a genuinely backdated raise cannot be applied to an already-run period.** That needs `effective_from` on the structure (migration + an HR field) and is only worth it once backdated raises are a real workflow. **Two options were rejected**: deriving the period's structure from `salary_structure_revisions.replaced_at` looks clever but that column records when HR *typed* the change, not when it took effect, so it silently mis-answers backdated or advance entry; and refusing to re-run a changed period adds friction we had just spent two rounds removing.

> 💸 **G22 — exit proration — and the far worse thing found while building it: `joining_date` was self-editable and already set pay.** The joining half of proration shipped in migration 035; the exit half did not exist, so `computeSlip` clamped the period *start* to `joining_date` and left the end at the month end unconditionally. Someone leaving on the 10th of a 31-day month was paid the whole month — ₹33,870.97 unearned on a ₹50,000 salary, the first time anyone resigns mid-month. Fixed symmetrically: an `effectiveEnd` mirroring `effectiveStart`, both leave queries clamped to the employed window at **both** ends (leave after someone left can no more exist than leave before they joined), and `preJoiningDeduction` renamed `notEmployedDeduction` since it now covers both ends.
> - **The real find: `joiningDate` and `lastWorkingDay` were in `PROFILE_FIELD_COLUMNS`** — the self-editable profile fields, alongside blood group and nearest airport — while `joining_date` already drove the payable-day count. An employee who genuinely started on the 20th could set the 1st from their own profile page and take the difference (**₹30,645.16** on a ₹50,000 salary in a 31-day month), or set a *future* date and be skipped by payroll entirely. `updateMyProfile` has no `profile_status` gate either, so this worked after verification and after months of payroll. Both dates are now HR-only (`PATCH /employees/:id/employment-dates`), sourced from the signed offer letter at verification time — **the point is that the value payroll trusts was never supplied by the person being paid.** Don't put them back.
> - **Payroll ignored `status` completely, and that was a second live defect.** `findSubtreeUsers` walks the tree with no status filter and `calculateForSubtree` never checked, so a deactivated employee with a verified profile and a salary structure kept receiving a full payslip, emailed to them, every month. Deactivation is the action HR *already* takes when someone leaves, so this is now its own skip — reported separately from the exit-date skip, because "account switched off" and "employment end date on record" are different things for HR to act on.
> - **Three skip reasons, deliberately distinct**: `"Account is no longer active"`, `"Already left before this period"`, `"Not yet joined for this period"`. Collapsing them into one would tell HR that something is wrong without telling them which record to fix.
> - **A future-dated leaving date needs no special case.** A notice period ending in a later month leaves `effectiveEnd` at the month end, so that month pays in full; the month after is skipped by the same comparison. Verified by test, not by argument.
> - **Changing either date is refused with `409` when a payslip already covers an affected period** — same reasoning as `assertPeriodsOpen`, and the affected range is bounded by the *old and new* values on each side, since moving a date in either direction changes the months between them. Void first, which reopens the period. This is deliberately the blocking form; the exit-action form that voids and regenerates in one step (agreed as the eventual shape) is not built yet.
> - **Any payslip that no longer agrees with an employee's employment dates is voided — never recomputed.** Both `PATCH /employees/:id/employment-dates` and `POST /employees/:id/exit` run the same check, and it compares **employed days**: a slip's `payable_days + lop_days` is the employed-day count it was built from, so if that differs from what the current dates imply, the slip is inconsistent and gets voided with a reason. Nothing is regenerated — HR re-runs payroll when they choose, and a `VOIDED` slip already returns the employee to `ok` in the run preview.
>   - **Two earlier designs were tried and both were wrong, which is exactly why the comparison is on days.** The first *replaced* the exit month's figures in place, so a departing employee would discover a pay cut by re-reading a payslip they had already read. The second refused a bare date edit with `409` and told HR to void the slip themselves — safe, but a dead end. **Both shared a deeper bug: they only ever looked at the month containing the leaving date.** A slip pro-rated by an *older* leaving date that later moved was never revisited, which underpaid a real employee — their June slip stayed at 14 payable days after the leaving date moved to 1 July, when they had worked all of June. **Reported from live use; no test caught it.** Comparing employed days instead of reasoning about which month the date falls in is what fixes it.
>   - **`payable_days + lop_days`, not `payable_days` alone** — otherwise every slip carrying any loss-of-pay looks inconsistent.
>   - **The employee is emailed about the void** (`sendSalarySlipVoidedEmail`, `MAIL_FEATURE_SALARY_SLIP_VOIDED`), and this is the one email that belongs in this flow. Silent voiding leaves someone holding a document that no longer applies; emailing the *corrected payslip* instead is how someone discovers a pay cut. The notice carries HR's reason and says a corrected payslip will follow — deliberately with **no figure**, because at the moment of voiding there isn't one yet. An ordinary HR void from the Salary Slips page sends the same email: a void is a void from the employee's side.
>   - **The `VOIDED` badge shows its reason on hover** (`SalarySlipList.jsx`, `Tooltip` with `portal` — required inside any table, whose `overflow-x-auto` wrapper both clips the floating label and counts its width toward `scrollWidth`). `Tooltip` returns bare children for a falsy label, so an `ACTIVE` badge is untouched.
>   - **A voided slip keeps its original figures**, because voiding only flips the status. That is right — it records what was issued — but it means a voided row still *displays* the old numbers, which reads as "it's still showing full pay" until you notice the status. That is what the hover reason is for, and it is how this bug was first reported.
> - **The five follow-ups this originally left open are now closed**, each in the smallest form that actually works:
>   - **`EMPLOYMENT_DATES_UPDATED` (migration 041)** tells the employee HR changed one of their dates. It quotes **no dates and no figures**, following `notifySalaryStructureUpdated`'s restraint for the same reason — a notification list is glanced at casually and often over someone's shoulder. One type covers both the plain edit and the exit, because from the employee's side it is one event.
>   - **Leave cannot start after the last working day**, checked in *two* places: at submit (`400`) and at approve/override (`409`). Two rather than one because the usual order of events is "book leave, then resign", so the leaving date normally arrives after the request. Payroll would clamp its window and ignore those days anyway — the reason to block is that the request would otherwise hold pending or taken days for a period the employee was not employed for.
>   - **The corrected payslip is deliberately NOT emailed — this was built, shipped, noticed in use, and taken back out.** The mechanics were fine (fired after the response, never awaited, the same shape `confirmPayroll` uses). What was wrong was what it does to a person: a corrected exit-month slip is almost always *smaller*, so the employee received a second payslip for a month they already had one for, quietly reduced, with no covering explanation — as a side effect of an HR admin recording a date. And a pro-rated slip is **not a final settlement**: notice pay, leave encashment and gratuity aren't modelled, so mailing it unprompted presents an incomplete figure as a final one. The same doc already said that and then emailed it anyway. The employee is still told in-app (`EMPLOYMENT_DATES_UPDATED` says a payslip was affected) and the corrected slip is in the app; who tells a departing employee what they will actually be paid is a conversation, not an automated attachment. **Don't re-add this without an explicit covering message and someone deciding it should go out.**
>   - **`npm run audit:employment-dates`** is a read-only report for the data that predates all of this. It exists because `joining_date` was self-editable while already driving pay, so every value in the database was either employee-entered or null and none was ever checked. It flags employees with no joining date (payroll treats null as "no restriction", so a mid-month joiner is overpaid) and — the urgent list — those whose date has **already been paid against**. Running it on the dev database immediately turned up two employees with payslips predating their joining date by a year, which is the kind of thing no amount of new validation would have surfaced.
>   - **`EmploymentDatesCard.jsx`** puts both actions on an HR surface, on the verification detail page (where HR has the offer letter in front of them, which is the moment the joining date is meant to be set) and on the employee details page. Two separate actions on purpose: **Save** edits a date and is refused when a payslip is in the way; **Record exit** is the operation that resolves that. The exit's success message names the periods voided and reissued, because HR has no other way to learn that a payslip's figures just changed.

> 🔒 **The payroll drift gap (G21) is closed by a per-employee period lock plus an overdue-request sweep — not by re-syncing payslips, and that distinction is the whole design.** A payslip stores `lop_days` as a snapshot and payroll only runs for a fully-completed period, so there was always a window between "the leave happened" and "payroll ran": any decision landing after the run left the slip and the leave record disagreeing, with nothing reconciling them. Six scenarios produced it (late approval, backdated submission, HR override in either direction, a second approval after the run, and flipping a leave type's `counts_as_lop`), and **five of the six overpay** — which nobody ever queries, so the error was biased toward silent loss.
> - **`assertPeriodsOpen` in `leaveRequestService.js` refuses a decision (409) when the request overlaps any period where that employee already holds an `ACTIVE` slip.** It sits in `decideLeaveRequest` — the single function every status change passes through — *after* `resolveActingCapacity` and `assertLegalTransition`, deliberately: an unauthorized caller must learn nothing about payroll, and an illegal transition is the more fundamental complaint.
> - **Only the four LOP-affecting actions are locked** (`APPROVE`, `REJECT`, `HR_OVERRIDE_TO_*`). `WITHDRAW` is deliberately left open — a `SUBMITTED` request never counted toward LOP (`findLopWorkingDays` filters on `APPROVED`), so withdrawing cannot invalidate a slip, and it is the employee's only remaining exit for a request that can no longer be decided. `CANCEL` needs no lock: it is already refused once the leave has started, and a slip only exists for a completed period.
> - **A request spanning two months is locked if *either* month has a slip** (`payPeriodsInRange`), because a request is charged **in full** to every period it overlaps — the documented no-pro-rating simplification. Checking only the end month would let it through and corrupt the earlier slip.
> - **Per-employee, derived from that employee's own `ACTIVE` slip — no `payroll_periods` table, no close/reopen action.** Voiding one person's payslip reopens exactly that person, which is already the documented correction path (void → decide → re-run). A company-wide close was considered and rejected as machinery that buys nothing here.
> - **The refusal is a 409 with the way out in the message**, naming the period and saying HR must void the payslip. A manager hitting this has never heard of a payroll run, so a bare "not allowed" would be a dead end.
> - **What the lock cannot see: flipping `counts_as_lop` on a leave type.** That changes historical LOP for every employee with no leave decision involved, so there is nothing to intercept. Catching it needs the reconciliation check (compare stored `lop_days` against a live `findLopWorkingDays`) — designed, **not built**, and still open.
> - **`sweepOverdueLeaveRequests` reports, it does not decide.** `SUBMIT` moves days into `pending` and only `APPROVE`/`REJECT`/`WITHDRAW` release them, so a request nobody ever decides shrinks an employee's balance permanently — true before the lock, and more reachable after it. The sweep notifies the manager (who can decide) and the employee (who can withdraw) once a request is 30+ days past its start date. **Auto-closing was rejected on audit-integrity grounds**: every version needs an actor recorded against the decision, and writing down a manager who never looked at it puts a false action in an append-only trail. A dedicated `EXPIRED` status would avoid that but changes what the employee sees — a product decision, still open.
> - **30 days is chosen against the payroll cycle**, not as a round number: payroll can only run once a period has ended, so 30 days is roughly when a request becomes undecidable because a slip now covers it.
> - **Two notification types for one event** (`LEAVE_REQUEST_OVERDUE` for the manager, `LEAVE_REQUEST_AWAITING_DECISION` for the employee), following the `MANAGER_REASSIGNED`/`TEAM_MEMBER_ASSIGNED` precedent. Not cosmetic: `notificationRouting.js` maps type → destination and takes no account of the viewer's role, so one shared type would have to send an employee to `/dashboard/approvals`, where `RequireRole` bounces them to `/403`.

> ⚠️ **Modal gotcha (already fixed, don't reintroduce):** `Modal`'s focus-on-open effect must depend on `open` only, **not** `onClose`. > ⚠️ **`setBusy(false)` must run on the success path too, not only in `catch` (already fixed in `TeamRequestList.jsx`, `MyLeaveRequestList.jsx`, `HolidayList.jsx` — don't reintroduce elsewhere):** the pattern `setBusy(true); try { await action(); onChanged(); } catch (err) { setError(...); setBusy(false); }` leaves `busy` stuck at `true` forever after a *successful* action, because `onChanged()` only refetches and re-renders the same row component with new props — it doesn't remount it, so `busy`'s state persists. Symptom: after a successful approve/reject/override/withdraw/cancel, the row's icon buttons show a permanent loading spinner (and, for reject, the inline comment box never closes), which reads as "the request is hanging" when it actually already succeeded instantly. Fix: always reset the loading flag in a `finally` block, and for the reject box specifically, explicitly close it (`setShowRejectComment(false)`) on success since nothing else does.

> ⚠️ **A query-param-triggered modal doesn't reliably re-trigger on an in-place navigation (already fixed, don't reintroduce):** the sidebar's "Apply Leave" link used to point at `/dashboard/my-leave?apply=1`, read via a lazy `useState` initializer on `MyBalancesPage` to auto-open the request modal. That works the *first* time you land on the page, but clicking the link again while already on `/dashboard/my-leave` is a search-only navigation — React Router doesn't remount the component for it, so the lazy initializer (which only ever runs once, at mount) never re-runs, and the click visibly does nothing. Fixed by giving "Apply Leave" its own real route (`ApplyLeavePage.jsx`, `/dashboard/apply-leave`) with the form embedded directly rather than in a `Modal` — a different route always mounts fresh, so the link is never a no-op regardless of where it's clicked from. It hands the new request's date back to `MyBalancesPage` via `navigate(..., { state: { focusDate } })` (router state, not a query param) so the calendar can still jump to it. General lesson: a query param meant to trigger a one-time action on an already-mounted page is fragile the moment that page can be reached without changing route — prefer a distinct route (or an explicit user action) over a query flag for anything that needs to "always do something" on click.
